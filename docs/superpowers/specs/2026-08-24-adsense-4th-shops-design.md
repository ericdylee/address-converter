# 애드센스 4차 재승인 설계 — "쇼핑몰별 실전 입력법" 축 신설

**작성일:** 2026-08-24
**배경:** 2026-08-24 애드센스 3차 거절. 사유 "가치가 별로 없는 콘텐츠(Low value content)".

---

## 1. 진단 — 무엇이 문제가 **아닌지** 먼저 확정한다

라이브 사이트(`https://address-converter.com`)를 직접 조회해 확인한 사실:

| 점검 항목 | 결과 |
|---|---|
| 14개 페이지 HTTP 응답 | 전부 200 |
| AdSense 스크립트 + `google-adsense-account` 메타태그 | 삽입됨 (`ca-pub-6010797332920736`) |
| `ads.txt` | 정상 (200, publisher ID 일치) |
| `robots.txt` / `sitemap.xml` | 정상 |
| 콘텐츠 분량 | 가이드 8편 + about/faq/privacy/contact, 편당 5,500~11,000자 |
| Search Console 색인 | 10개 이상 (거의 전 페이지) |
| 실제 유입 | 하루 10명 이상 |

**따라서 기술 세팅·분량·색인·유입은 원인이 아니다.** 지난 3차까지의 처방("글을 더 쓰자")은 이미 소진됐고, 같은 처방을 반복하면 4차도 같은 결과가 나온다.

### 확인된 원인 1 — 주제 중복

가이드 8편의 핵심어 출현 빈도(본문 텍스트 추출 후 집계):

| 가이드 | City | State | ZIP/Postal | 동·호수 | "Teheran" 예시 |
|---|---|---|---|---|---|
| english-address | 9 | 8 | 8 | 16 | 4 |
| common-mistakes | 8 | 7 | 4 | 12 | **13** |
| korea-region-names | 15 | 11 | 2 | 1 | 0 |
| overseas-shopping | 11 | 12 | 8 | 12 | 0 |
| japan-address | 12 | 10 | 1 | 12 | 1 |

8편 중 5편이 "City·State 칸에 무엇을 넣나 + 동/호수 표기"라는 동일 주제를 각도만 바꿔 반복하고, 예시 주소(테헤란로 152)까지 공유한다. 구글이 거절 메일에서 링크한 [thin content 가이드라인](https://support.google.com/webmasters/answer/9044175)의 *"부가가치가 거의 없는 콘텐츠"*에 정확히 해당한다.

### 확인된 원인 2 — 사이트 고유의 것이 없다

- 도구(`/result`)의 출력은 전량 행정안전부 API 결과 = **서드파티 콘텐츠**
- 가이드 8편은 그 도구의 사용 설명서 = **파생 콘텐츠**
- 구글 입장에서 이 사이트만의 것은 "칸 분리 + 복사 버튼" UI뿐

### 확인된 원인 3 — 운영 주체·최신성 신호 부재

- 가이드 8편 전부 작성자 표기 없음
- `lib/structured-data.ts`의 `GUIDE_DATE = "2026-07-14"` 상수가 **8편 모두에 동일 적용** — 개별 작성일/수정일이 없다
- `articleSchema`의 `author`가 `Organization`(사이트 이름)이라 사람이 없다
- `sitemap.xml`의 `lastmod`가 2026-07-14 → 3차 거절 이후 6주간 사이트 무변경. 구글은 **지난번 거절한 것과 동일한 사이트**를 재검토했다

## 2. 목표

구글 재검토자가 사이트를 열었을 때 **"이 사이트에만 있는 것"이 즉시 보이도록** 만든다. 부수 효과로 검색 유입도 늘린다(둘은 같은 방향이다).

### 비목표 (YAGNI)

- 글 편수 늘리기 자체 — 이미 실패한 처방이다
- 프로그래매틱 SEO(우편번호별 자동 생성 페이지 등) — thin content 판정을 **악화**시킨다
- 도구 신기능(영문 주소 점검기, 역변환) — 좋은 아이디어지만 이번 거절 사유를 직접 겨냥하지 않는다. 4차도 실패하면 그때 착수한다
- 기존 가이드 8편 삭제 — 색인·유입이 이미 붙어 있어 잃을 게 크다. 삭제가 아니라 **차별화**한다

## 3. 설계

### 3.1 정보 구조 — 새 섹션 `/shops`

성격이 다른 콘텐츠라 폴더를 분리한다. 사용자와 크롤러 양쪽에 "이 사이트는 두 종류의 콘텐츠를 가진다"가 드러난다.

```
/guide          기존 8편 — 원리 설명서 ("영문 주소란 무엇이고 어떻게 쓰나")
/shops          신규 목록 페이지
/shops/amazon   신규 실전편 — "이 사이트의 이 칸에 이걸 넣으세요"
/shops/iherb
/shops/aliexpress
```

- `components/Header.tsx`의 `NAV`에 `{ href: "/shops", label: "쇼핑몰별" }` 추가 (소개·가이드 사이)
- `components/Footer.tsx`에도 동일 링크 추가
- `app/sitemap.ts`에 4개 URL 추가 (`/shops` 0.8, 각 편 0.8)
- 기존 `/guide/overseas-shopping`에서 3편 각각으로 문맥 링크, 역방향도 연결

`/shops`를 고른 이유: 3편 모두 쇼핑몰이고, 나중에 배대지·페이팔이 붙어도 "해외 구매 관련"으로 묶인다. 편수가 늘면 그때 재검토한다.

### 3.2 실전편 1편의 구성 — 여기가 승부처

각 편에 반드시 들어가는 요소. **이 목록에서 빠지는 항목이 있으면 그 편은 기존 가이드와 다를 게 없다.**

| 요소 | 목적 | 출처 |
|---|---|---|
| 실제 주소 폼 캡처(주석 표시) | 구글이 "다른 데도 있는 내용"이라 부를 수 없는 유일한 자산 | 대표님 제공 |
| 그 사이트의 **실제 필드명 그대로** → 넣을 값 표 | 일반론이 아니라 그 화면에 대한 설명 | 캡처에서 판독 |
| **이 사이트만의 함정** | 고유성의 핵심. 3편이 서로 달라야 하는 이유 | 캡처 + 대표님 경험 |
| 틀렸을 때 뜨는 **실제 에러 메시지**와 해결법 | 직접 겪지 않으면 못 쓰는 내용 | 대표님 제공(선택) |
| 입력 후 **어디서 다시 확인하는지** | 실사용 흐름의 마무리 | 캡처 |
| `최종 확인: YYYY-MM-DD 화면 기준` 표기 | 관리되는 사이트라는 신호 | 자동 |
| 변환기 CTA + 관련 가이드 링크 | 사이트 내 순환 | 기존 `GuideCta` 재사용 |

**작성 규칙 (엄수):**

> 캡처에서 직접 읽히지 않는 사실은 쓰지 않는다. 필드명·에러 문구·버튼 라벨은 전부 캡처와 대조해 확인한 뒤 적는다. 기억이나 추측으로 채운 문장은 이 작업의 목적을 정면으로 배반한다.

미확인 항목은 초안에 `⚠️미확인` 으로 남겨 대표님 확인을 받고, 확인되지 않으면 **문장을 삭제**한다.

### 3.3 E-E-A-T — 날짜와 작성자

**날짜:**
- `lib/structured-data.ts`의 `GUIDE_DATE` 상수 제거
- `guideJsonLd(opts)`에 `datePublished` / `dateModified`를 개별 인자로 받도록 변경 (기존 8편 호출부 전부 수정)
- 각 글의 실제 작성일은 git 이력에서 확인해 넣는다
- 화면 하단에 `최종 확인: YYYY-MM-DD` 표시하는 공용 컴포넌트 신설 (`components/LastVerified.tsx`)

**작성자:**
- `articleSchema`의 `author`를 `Organization` → `Person`(실명)으로 변경
- `lib/site.ts`에 `AUTHOR_NAME` 상수 추가
- `app/about/page.tsx`에 운영자 소개 섹션 추가 — 이름, 왜 이 사이트를 만들었는지, 무엇을 근거로 관리하는지

### 3.4 기존 8편 중복 정리

각 편의 역할을 하나로 못박고, 겹치는 문단은 **삭제 후 링크로 대체**한다. 예시 주소도 편마다 다르게 바꾼다.

| 가이드 | 확정 역할 | 조치 |
|---|---|---|
| english-address | 원리 총론 (허브) | 유지. 다른 편으로 나가는 허브 역할 강화 |
| common-mistakes | 실수 사례집 | 기본 원리 설명 문단 삭제 → english-address 링크. 예시 주소 교체 |
| korea-region-names | 시·도 표기 사전 | 표 중심으로 좁힘. City/State 원리 설명은 링크 |
| apartment-unit | 상세주소 표기 | 유지 (역할 명확) |
| overseas-shopping | 해외 양식 일반론 | `/shops` 3편으로 가는 관문으로 재배치 |
| international-shipping | EMS·세관 라벨 | 유지 (역할 명확) |
| japan-address | 일본 주소 | 유지 (역할 명확) |
| english-documents | 서류용 | 유지 (역할 명확) |

**예시 주소 배정** (테헤란로 152 중복 해소):

| 가이드 | 사용할 예시 |
|---|---|
| english-address | 서울 강남구 테헤란로 152 (기존 유지 — 허브) |
| common-mistakes | 부산 해운대구 (신규) |
| overseas-shopping | 경기 성남시 분당구 (신규) |
| korea-region-names | 시·도별 대표 주소 (표에서 이미 분산) |

### 3.5 이미지 파이프라인

- 저장 위치: `public/shots/<사이트>/<번호>-<설명>.png`
- `next/image`로 렌더 (`width`/`height` 명시 → CLS 방지)
- `alt` 텍스트 필수 — 화면에 보이는 내용을 문장으로 서술 (접근성 + 색인)
- **개인정보 마스킹 필수** — 실제 이름·주소·이메일·전화번호·주문번호·통관부호는 게시 전 가린다. 원본 캡처에 남아 있으면 배치 전에 마스킹한다
- 캡처는 주소 입력 폼 영역만 크롭 (사이트 UI 전체를 통째로 싣지 않는다 — 인용 목적 범위 유지)
- 이미지 주석(화살표·번호)은 캡처 위 CSS 오버레이가 아니라 이미지 옆 설명 목록으로 처리 (다크모드·확대 대응, 텍스트가 색인됨)

### 3.6 재제출 절차

```
1. 배포 (main 병합 → Vercel 자동배포)
2. Search Console에서 신규 URL 4개 색인 요청 (/shops, /shops/amazon, /shops/iherb, /shops/aliexpress)
3. 1~2주 대기 — 새 페이지가 실제로 색인되고 노출되기 시작할 때까지
4. Search Console '페이지' 메뉴에서 신규 4개 URL이 "색인 생성됨"으로 바뀐 것을 확인
5. 그 다음 애드센스 '검토 요청' 클릭
```

**4번을 확인하기 전에는 재제출하지 않는다.** 3차 실패의 직접 원인이 "변경 없는 사이트 재제출"이었다.

## 4. 대표님이 준비할 캡처 목록

각 사이트에서 **주소 입력 폼**을 캡처한다. 로그인 후 배송지 추가/수정 화면이면 된다(실제 주문 불필요).

**사이트당 필요한 것:**

1. **빈 주소 입력 폼 전체** — 모든 칸 이름이 보이게. 이게 가장 중요하다
2. **입력을 마친 폼** — 실제 값이 들어간 상태 (개인정보는 제가 가립니다)
3. **저장된 주소가 표시된 화면** — 목록이나 확인 화면
4. (있으면) **에러 메시지** — 잘못 넣었을 때 뜨는 경고
5. (아이허브·알리) **개인통관고유부호 입력란**이 보이는 부분

**형식:** PNG, 화면 그대로. 가독성을 위해 브라우저 확대(⌘+)를 한두 단계 올리고 찍으면 좋다.

**전달 방법:** 파일명은 자유롭게 두고 사이트별로 폴더만 나눠 아래 경로에 넣어 주시면 됩니다. 정리·마스킹·리네이밍은 제가 합니다.

```
public/shots/amazon/
public/shots/iherb/
public/shots/aliexpress/
```
